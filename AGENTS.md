# AGENTS.md — `HiveMind-HackChatBridge`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

Bridges a [hack.chat](https://hack.chat) channel to a HiveMind hub: a HiveMind
bridge is a satellite whose input and output are a chat channel instead of a
microphone. Channel messages become `recognizer_loop:utterance` bus messages;
the hub's `speak` reply (and `hive.complete_intent_failure`) is posted back
into the channel, addressed to the originating user. Part of the
[HiveMind](https://github.com/JarbasHiveMind) ecosystem — a protocol for
connecting satellite devices to a hub running
[OpenVoiceOS](https://github.com/OpenVoiceOS). The hub is
[HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core); the client
library is
[hivemind-bus-client](https://github.com/JarbasHiveMind/hivemind-bus-client).
Sibling bridges with the same shape (chat platform in, chat platform out):
`hivemind-telegram-bridge`, `HiveMind_mattermost_bridge`, and the other
chat-platform bridges under the org — check them for prior art before
inventing a new pattern here.

## Layout / build / test

- Package module: `hackchat_bridge/`. Tests live in `tests/` (`tests/e2e/`
  holds the live-hub suite — check before adding, do not create a second test
  directory).
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[test]" --prerelease=allow`
- Run the smoke suite in the foreground: `python3 -m pytest tests -q
  --ignore=tests/e2e`. It fakes `HiveMessageBusClient` and never calls
  `connect_hackchat()`, so it never opens a real websocket to hack.chat or a
  hub — treat it as a shape/wiring check, not a live-behaviour guarantee.
- `tests/e2e/` boots a real `hivemind-core` hub via `hivescope` and drives the
  bridge's production `HiveMessageBusClient` path over a real loopback
  WebSocket (`.[e2e]` extra), using the published `hivescope` release
  (>=0.8.0a1).
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is
  a bug to FIX at the source, not to work around with a pin downgrade.

## Dependencies

- **Floor pins only** (`>=X.Y.Za1`), bumped when a feature or fix is actually
  needed — with a one-line comment saying why. No upper caps unless a specific
  released version is genuinely broken (say which and why). The current
  `hivemind-bus-client<2.0.0` upper cap in `requirements.txt` should be
  revisited the same way: keep it only if a real 2.x break is known, otherwise
  drop it.

- Everything in `pyproject.toml`/`requirements.txt` (deps, metadata, version).
  Never install from git — depend on a published PyPI alpha.
- Apache-2.0. Do not add GPL/AGPL dependencies.

## Tests

- Adversarial by default. A regression test must **fail before the fix and pass
  after** — prove it by reverting only the source (`git apply -R`, never
  `git stash` across worktrees) and watching the test flip.
- Tests must be mutation-proof: gutting the feature must fail the test. A test
  that only asserts a mock was called, without asserting the real behaviour, is
  weak — note it.
- Never skip a test because an optional dependency is missing.
- CI green is permission to review, not to merge. A non-trivial change gets an
  adversarial review before it lands.

## Repo-specific rules

- **Composition, not inheritance — but connect it in `__init__`, not later.**
  `JarbasHackChatBridge` accepts an injected `bus`; if none is given it builds
  its own `HiveMessageBusClient` **and connects it right there** in
  `__init__`, before `run()` is ever called. This differs from the
  telegram-bridge pattern (build in `__init__`, connect in `start()`); do not
  "fix" it to match that pattern without checking callers — `tests/e2e`
  and any script that constructs `JarbasHackChatBridge` without a bus relies
  on the connection existing immediately after construction. Never add a
  second `.connect()` or `.run_forever()` call — `run()` calls
  `connect_hackchat()` then `self.bus.run_forever()` exactly once.
- **`connect()` must bound `handshake_max_retries`.** The
  `hivemind-bus-client` floor is `>=1.0.13a1`; that client's own default for
  `handshake_max_retries` on `connect()` is `None`, meaning retry forever.
  This bridge already passes a bounded value (`handshake_max_retries=10` by
  default, exposed as a constructor parameter) — keep it that way. Any change
  to the connect path must keep an explicit finite bound; a bridge that calls
  `connect()` unbounded hangs indefinitely against a stalled or unreachable
  hub instead of failing fast.
- **The hub owns ACL, not this bridge.** A freshly registered HiveMind client
  is denied every message type until an admin runs `hivemind-core allow-msg
  recognizer_loop:utterance <client_id>` (and usually `speak`,
  `hive.complete_intent_failure`). This bridge has no way to grant itself
  permissions and must not try to work around a denial locally — a silently
  dropped message on the hub side is the hub doing its job, not a bug here.
- **Rejected credentials must fail fast.** The bounded
  `handshake_max_retries` is what turns "wrong access key/password" into a
  clean failure instead of a bridge that spins forever looking connected. Do
  not add retry/backoff logic on top of `connect()` that defeats this.
- **Forward upstream responses verbatim.** `handle_speak()` prefixes the
  hub's `speak` utterance with `@<user> , ` (so hack.chat addresses the right
  person) and relays the rest unmodified — do not reformat, truncate, or
  otherwise decorate hub-authored text beyond that addressing prefix. The
  `hive.complete_intent_failure` fallback line ("I don't know how to answer
  that") is bridge-authored by design, because the hub sent no utterance to
  relay.
- **Thread safety.** `HackChat.run()` (the hack.chat receive loop) and the
  HiveMind bus's own worker thread run on separate daemon threads
  (`ovos_utils.create_daemon`); there is no asyncio loop here, so a new
  callback path only needs to avoid shared mutable state across those two
  threads (e.g. `online_users`) without a lock — keep new handlers as small,
  self-contained functions the way `on_hack_join`/`on_hack_leave` are.
